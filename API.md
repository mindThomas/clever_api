# Clever mobile API reference

## Clever Power household consumption (read-only)

The following app routes were verified with read-only requests on 2026-11-24.
They use the existing REST base URL, authentication and response wrapper.

| Method | Relative path | Parameters |
| --- | --- | --- |
| GET | `powerconsumption/powerEngagements` | None |
| GET | `powerconsumption/daily/gsnr/{gsnrId}` | `startDate=YYYY-MM-DD` |
| GET | `powerconsumption/monthly/gsnr/{gsnrId}` | `startDate=YYYY-MM-DD` |
| GET | `powerconsumption/yearly/gsnr/{gsnrId}` | `startDate=YYYY-MM-DD` |

Engagements contain `powerMeterEngagementInfos[]`, with `gsrn`, agreement
start/end dates, associated chargepoints and address details. Select the
appropriate active agreement; do not assume every account has only one meter.
Never publish engagement responses, which contain customer-specific data.

Consumption responses contain `totalConsumption` with:

- `totalPowerMeterkWh`: total main-meter consumption, **including charging**.
- `totalChargePointkWh`: the associated charging consumption.
- `powerConsumptionPrPeriod[]`: timestamped rows with `date`,
  `powerMeterConsumptionkWh`, `chargePointConsumptionkWh` and `chargePoints`.

Household consumption excluding charging is main-meter consumption minus
chargepoint consumption. The same subtraction applies to individual rows.
For example, synthetic values of 20 kWh and 5 kWh give 15 kWh for the household.

Use a calendar date for `startDate`: the selected day, first day of the month,
or first day of the year. Daily rows are hourly and use UTC timestamps; convert
these to the installation's local timezone before displaying clock times.
Monthly and yearly row dates label calendar periods: do not blindly apply
hourly timestamp bucketing to those date labels. Current periods can be
incomplete or revised; these endpoints are historical energy, not live power.

The client exposes `get_power_engagements()` and
`get_power_consumption(meter_id, start_date, period)`.

The sensor platform discovers active meters and adds a monthly household sensor
and a latest-published-day household sensor per meter. The monthly sensor carries
daily, monthly and hourly chart data and an explicit latest-published date.
These are historical period values, not lifetime counters, and are deliberately
not assigned a cumulative statistics state class. A separate six-hour coordinator
handles updates and failures without marking charging entities unavailable.
No control services, config-entry migrations or charging commands are added.

## Read-only app electricity prices and historical surcharges

`get_electricity_prices(address_id, start_date, end_date)` reads
`GET electricity-pricing/app-price` with `darReferenceId`, `from` and `to`.
Both dates use `YYYY-MM-DD`. The sensor requests today and tomorrow every
20 minutes, exposing the current interval's `totalPrice` in DKK/kWh, with
timestamped `prices` attributes and the API's tariff breakdown. Negative prices
are preserved. Unsupported units, missing values and invalid intervals fail
instead of becoming zero. Data is limited to the intervals Clever publishes;
it is not a forecast generated by this integration.

`get_historical_energy_surcharges(start_date, end_date)` reads
`GET energysurcharge/historical` with `startYear`, `startMonth`, `endYear` and
`endMonth`. A separate daily coordinator requests this year and the two preceding
calendar years. Its sensor shows the latest published monthly surcharge, with
the month explicitly identified, and exposes history containing the published
rate, average price and cutoff threshold. Zero is a valid published rate. This
does not replace the existing estimated current-month surcharge sensor.

Price sensors are discovered per active delivery address; surcharge history is
account-scoped and also works without a Clever Power agreement. Each data source
has independent update/availability handling. Neither is used as a charging
decision input, and no existing prices, analytics or charging controls change.

This is an unofficial, implementation-oriented reference derived from Clever
Android app 26.33.0 and read-only response inspection. Clever does not publish
this as a supported public API and may change it without notice.

No account credentials, bearer tokens, refresh tokens, or captured customer
data belong in this document or in repository fixtures.

## Authentication and transport

- The app signs in through Firebase Identity Toolkit using email and password.
- Subsequent Clever requests use the Firebase ID token as a bearer token.
- ID tokens are renewed through Firebase Secure Token using a refresh token.
- The integration stores the refresh token, never the password.
- Clever REST routes use the mobile backend v6 base URL.
- Live documents come from the `user-database` Firestore database in the
  `clever-app-prod` project, scoped below `v1-user-data/{firebaseUserId}`.
- Mobile app identity/version headers are required by the backend. Their current
  values are implementation details in `clever/clever.py`, not user secrets.

| GET | `installations` | Home charger, connector, model, and capabilities |
| GET | `consumption/history` | Completed charging sessions and energy |
| GET | `energysurcharge/estimated` | Current estimated energy surcharge |
| GET | `chargingprofiles` | Smart-charging configuration |
| PUT | `chargingprofiles/{id}/enable` | Enable or disable a profile |

| PUT | `chargingprofiles/{id}/power-required` | Set required energy in kWh |
| PUT | `chargingprofiles/{id}/preheat` | Enable or disable preheating |
| POST | `smartcharging/chargePoints/{chargePointId}/connectors/{connectorId}/boost` | Boost the active session |
| POST | `smartcharging/chargePoints/{chargePointId}/connectors/{connectorId}/timebox-boost` | Timed boost |
| POST | `smartcharging/chargePoints/{chargePointId}/connectors/{connectorId}/unboost` | Cancel boost |

| Firestore | `active-transactions` | Live session, consumption, plan, and vehicle state |

### Active transaction fields

| Field | Meaning | Home Assistant exposure |
| --- | --- | --- |
| `cpmsChargingStatus` | Charging, suspended, completed, or faulted state | Charger state and charging binary sensor |
| `chargingStart` | Session start timestamp | Expected-completion attributes and duration calculation |
| `chargingEnd` | Session end timestamp, when present | Duration calculation |
| `consumedWh` | Energy delivered in the session | Session energy |
| `smartChargingFlow` | Smart-charging strategy | Parsed for future diagnostics |
| `chargingPlan.powerRequiredInKwh` | Expected/target session energy | Target energy and progress |
| `chargingPlan.departureTime` | Planned departure | Expected-completion attributes |
| `chargingPlan.earliestFinishedAt` | Earliest expected completion | Expected completion |
| `chargingPlan.postponedUntil` | Planned charging delay | Expected-completion attributes |
| `chargingPlan.segments[]` | Scheduled start/end, energy, and reason | Boost detection |
| `vehicleStateOfCharge.vehicleChargeState.batteryLevel` | Vehicle battery percentage, when linked | Vehicle battery level |
| `vehicleStateOfCharge.vehicleChargeState.chargeLimit` | Vehicle charge limit | Battery sensor attribute |
| `vehicleStateOfCharge.vehicleChargeState.isPluggedIn` | Vehicle connection state | Connected binary sensor |

The Android transaction model contains no instantaneous power field. The
integration therefore exposes **average session power**, calculated as delivered
kWh divided by elapsed session hours. It is not a current-rate measurement.
